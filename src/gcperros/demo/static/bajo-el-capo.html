El recorrido de un evento

  1. Producir

    Partidoposesiones, pases, remates; misma semilla, mismo partido Cuotastres operadores que reaccionan con retraso

  2. Transportar

    Pub/Submatch-events y odds-updates, cada uno con su dead letter

  3. Procesar

    Motordeduplicar → reordenar por marca de agua → aplicar Señalesmodelo propio frente al precio vigente

  4. Guardar

    Firestorelive_matches: un documento vivo por partido BigQuery Rawgcperros_raw: cada mensaje, crudo, sin interpretar BigQuery analíticogcperros_analytics: modelo estrella

Lo que ves en «En vivo» es el documento de Firestore tal cual, más reloj y posesión. La página no conoce el motor: el día que esto se despliegue, cambia la fuente y la página no.

Dos bases, dos trabajos

Firestore
Para mirar ahora. Un documento por partido, ya calculado: el panel lo escucha en vez de consultarlo.
BigQuery
Para preguntar qué pasó. La capa Raw guarda cada mensaje sin interpretar y el motor no la lee nunca: es el archivo del que se recalcula todo.

Una consulta de un partido en un día lee una partición de cada diez y, dentro, sólo los bloques de ese partido. Con el modelo de costes de la HU-23, eso es alrededor de un 2 % de los datos de una lectura completa.

Es una estimación, no una medición: nada está desplegado todavía y no hay un plan de ejecución real de BigQuery detrás. Se medirá cuando exista el proyecto de GCP.

Lo que se despliega

  • 2 topics de Pub/Sub, cada uno con su suscripción y su dead letter
  • 2 datasets de BigQuery, Raw y analítico, con sus tablas
  • 1 base de Firestore en modo nativo
  • 4 cuentas de servicio con permisos mínimos, sin llaves descargadas
  • Artifact Registry para la imagen del motor; el servicio de Cloud Run se declarará al desplegarlo

Todo declarado en Terraform y validado en cada cambio por la integración continua. Todavía no se ha ejecutado terraform apply: hace falta un proyecto con facturación.
